# SOAR-0016: Attached macros on generated declarations

Attach user-provided Swift macros to generated types and methods through the generator configuration.

### Introduction

Add an `attachedMacros` configuration key that attaches macros to selected generated declarations.

### Motivation

Generated code is rewritten on every build, so adopters can't add attributes to generated declarations. The only options today are post-processing the output or forking the generator.

Extensions can't cover these cases, because they can't add stored or `$`-prefixed members, generate new types from the shape of a generated type, or keep up with the document automatically:

- **Shared handling of responses.** Every response has an optional `error` field, and the adopter wants every operation output to conform to a common protocol.
- **Publisher variants of client methods.** A peer macro, similar to [`AddAsync`](https://github.com/swiftlang/swift-syntax/blob/main/Examples/Sources/MacroExamples/Implementation/Peer/AddAsyncMacro.swift), generates a Combine variant of each client method.
- **Test mocks.** [Mockable](https://github.com/Kolos65/Mockable) generates a mock from a protocol annotated with `@Mockable`. Today, the mock for `APIProtocol` is written and maintained by hand.
- **Dependency clients.** [swift-dependencies](https://github.com/pointfreeco/swift-dependencies)' `@DependencyClient` needs a struct of closures, so adopters write a wrapper around `Client` by hand and update it whenever the document changes.

The adopter, or a library, already has the macro. What's missing is a way to tell the generator where to attach it.

### Proposed solution

A new optional `attachedMacros` key in the configuration file, following the structure of the OpenAPI document:

```yaml
additionalImports:
  - Mockable
  - PetStoreMacros
attachedMacros:
  components:
    schemas:
      - match: ".*"
        macros:
          - name: MyMacro
      - match: "^Pet$"
        macros:
          - name: PetMacro
            arguments:
              - label: name
                value: '"Pet"'
  operations:
    - match: ".*"
      output:
        - name: APIErrorReporting
  apiProtocol:
    - name: Mockable
    - name: DependencyClientWrapper
      arguments:
        - label: name
          value: '"PetStoreClient"'
```

This produces, among others:

```swift
/// - Remark: Generated from `#/components/schemas/Pet`.
@MyMacro
@PetMacro(name: "Pet")
public struct Pet: Codable, Hashable, Sendable { ... }
```

```swift
@Mockable
@DependencyClientWrapper(name: "PetStoreClient")
public protocol APIProtocol: Sendable { ... }
```

The generator only attaches the macros. The adopter lists the modules that define them in `additionalImports`.

Without `attachedMacros`, the generated code is unchanged.

Both the generated `Client` and server handler types conform to `APIProtocol`, so a macro on `APIProtocol` covers client and server adopters alike. For example, a mock generated by `@Mockable` can stand in for the client in tests of code that calls it, and for the handler in tests of code that hosts the server.

### Detailed design

#### Targets

| Key | Attached to |
| --- | --- |
| `components.schemas` | `Components.Schemas.<Name>` |
| `components.parameters` | `Components.Parameters.<Name>` |
| `components.requestBodies` | `Components.RequestBodies.<Name>` |
| `components.responses` | `Components.Responses.<Name>` |
| `components.headers` | `Components.Headers.<Name>` |
| `operations[].input` | `Operations.<Op>.Input` |
| `operations[].output` | `Operations.<Op>.Output` |
| `operations[].clientMethod` | The `Client` method of the operation |
| `apiProtocol` | `APIProtocol` |
| `client` | `Client` |
| `server` | `APIProtocol.registerHandlers(on:serverURL:configuration:middlewares:)` |

The other component kinds, such as examples, links, callbacks, and security schemes, don't produce generated declarations.

Macros are attached only to the top-level declaration of a matched item, not to nested types.

#### Matching

`components.*` and `operations` are lists of rules. Each rule has a `match` regular expression:

- It's matched against the OpenAPI name: the component key (for example `pet-store`, not `PetStore`), or the `operationId`. An operation without an `operationId` uses the identifier the generator already synthesizes from its method and path, such as `get/pets/{petId}`.
- A rule matches if the regular expression matches anywhere in the name. Use `^Pet$` for an exact match and `.*` to match everything.
- Matching is case-sensitive.
- Every matching rule contributes, in rule order.
- An invalid regular expression is an error.

Rules are a list rather than a mapping keyed by regular expression, because decoding a YAML mapping doesn't preserve key order, so macro order wouldn't be deterministic.

#### Macros

Each macro is an object:

- `name`: the macro name, without the leading `@`. The generator adds the `@`. A name starting with `@` is an error.
- `arguments` (optional): a list of arguments, each with an optional `label` and a `value`. The `value` is Swift source, emitted verbatim. For example, a string argument is written `value: '"Pet"'`, and an enum case is written `value: .live`.

The generator doesn't validate macro names or argument values. A mistake results in a compilation error in the generated code.

Each macro is emitted on its own line, after the documentation comment and before the declaration's existing attributes.

### API stability

- No changes to the runtime, transports, or middlewares.
- A new optional `attachedMacros` key in the configuration file. Existing configuration files remain valid, and generated code is unchanged unless the key is used.

### Future directions

- Targets for nested types, such as inline schemas or `Input.Query`.
- More ways to match operations, such as by tag or path.

### Alternatives considered

#### Raw attribute strings

An earlier draft accepted attributes as strings, such as `"@DependencyClientWrapper(name: \"PetStoreClient\")"`. Structured entries drop the redundant `@` and make arguments explicit.

#### A wildcard `*` and exact-name keys

An earlier draft used `"*"` to match everything, next to exact names. Regular expressions cover both with a single rule, plus patterns such as prefixes.
