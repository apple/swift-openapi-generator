# SOAR-0017: Declaration-Based Types File Splitting

Allow large generated types namespaces to be split into smaller extension files using an optional declaration limit.

### Introduction

This proposal adds an advanced, opt-in sharding strategy for generated Swift types. The `output.maxDeclarationsPerFile` control lets adopters limit the number of immediate namespace members in each generated types file, placing overflow declarations in additional extension files. This gives adopters control over file granularity to tune downstream Swift compilation without changing generated API symbols.

### Motivation

The generator currently splits types into separate files by namespace. This can improve downstream Swift build times, but the benefit is limited when most of an API's generated code belongs to a single namespace. APIs with a large proportion of schemas can still place most of their generated source in `Types+Components+Schemas.swift`, while the other output files remain small. That one large file can continue to dominate compilation time.

Namespace boundaries alone cannot divide this work further. Adopters who need smaller files must post-process generated Swift, preserving declarations, comments, and imports themselves. A declaration limit would let the generator divide large namespaces into smaller files directly, giving adopters more control over file granularity and opportunities for parallel compilation.

Keeping this control opt-in preserves the normal output layout for existing users while allowing adopters with especially large namespaces to choose a limit suited to their API and build environment.

### Proposed solution

Add an optional `output.maxDeclarationsPerFile` setting to the generator configuration:

```yaml
generate:
  - types
output:
  maxDeclarationsPerFile: 100
```

The limit must be a positive integer. It applies independently to `Operations` and each supported second-level `Components` namespace: `Schemas`, `Parameters`, `RequestBodies`, `Responses`, and `Headers`.

For a `Schemas` namespace containing 250 immediate declarations, the example configuration emits:

```text
Types+Components+Schemas.swift       # first 100 declarations
Types+Components+Schemas+1.swift     # next 100 declarations
Types+Components+Schemas+2.swift     # final 50 declarations
```

The first chunk keeps the existing unsuffixed filename. Only overflow chunks receive numeric suffixes, starting at `1`. A namespace that fits within the limit produces no additional files. Empty namespaces retain their unsuffixed files.

When the setting is omitted, the generator continues to emit the normal eight files. Client and server generation are unaffected. The direct command-line interface and command plugin support the setting; the SwiftPM and Xcode build-tool plugin rejects it because its output files must be declared before generation.

### Detailed design

#### Counting and partitioning declarations

The types translator collects each supported namespace's immediate generated declarations in their existing generation order and partitions that sequence into contiguous chunks of at most the configured size.

A schema declaration counts as one member, including any properties and nested declarations it contains. An operation namespace likewise counts as one member, including its input and output types. Nested declarations are not split recursively. Namespace containers, imports, comments, and root declarations such as `APIProtocol` and `Servers` are outside the count.

For a namespace with `D` members and a configured limit `N`, the generator emits `max(1, ceil(D / N))` declaration-bearing files. Each file carries the required imports and generated file comments and extends the same namespace.

The configuration is decoded from the optional `output` mapping and passed to types generation. A value of zero or less produces an error rather than an empty or unbounded partition. No separate command-line flag or feature flag is proposed.

#### Build-tool plugin support

The current SwiftPM and Xcode build-tool plugin declares its outputs before invoking the generator. Unlike the fixed namespace layout, the numbered overflow files cannot be determined from the generator modes alone.

The plugin therefore rejects a configured declaration limit for types generation, even if a particular document would not overflow. Generation without the setting continues to use the existing fixed output declarations. Supporting this option in the build-tool plugin would require a prebuild command or another mechanism for discovering dynamic outputs and is deferred to separate work.

### API stability

This proposal preserves the generated Swift API and requires no changes to the runtime, its Generated SPI, transports, or middleware. The configuration option is additive and opt-in; existing configurations and CLI arguments remain valid. Generated file counts and names are implementation details, as documented in <doc:API-stability-of-the-generator>.

### Future directions

Future work could support dynamic outputs in the build-tool plugin, provide a manifest or safe cleanup mechanism for stale generated files, or investigate per-namespace limits if a single limit proves insufficient.

Declaration-count splitting does not account for dependencies between generated types. A future dependency-aware strategy could group types into layers and expose those layers as separate build targets, allowing prerequisite layers to compile before the layers that depend on them.

### Alternatives considered

#### Configure the number of output files

An alternative is to configure the desired number of files rather than the maximum number of declarations per file. For example, passing `N = 20` would ask the generator to evenly divide the declarations across 20 files, with declaration counts differing by at most one between files.

A major advantage is compatibility with the SwiftPM and Xcode build-tool plugin model: with a fixed file count and deterministic filenames, the plugin could read the configured count and declare all outputs before generation, without a prebuild command. The generator would need to emit every declared file, including empty files when there are fewer declarations than files. This would make build-tool plugin support possible with corresponding plugin changes.

The tradeoff is that the number of declarations in each file grows as the API grows. A maximum declaration count instead bounds the number of immediate members per file and allows the file count to grow with the API. Neither approach guarantees equal compilation work across files, since individual declarations can vary substantially in size and complexity.
